### 1.2 O que cada referência é, e o que não é

- **OWASP Top 10** classifica riscos. Não é checklist de verificação nem norma.
- **OWASP ASVS** lista requisitos verificáveis. O próprio projeto diz, em `0x04-Assessment_and_Certification.md` (v5.0.0): *"OWASP, as a vendor-neutral nonprofit, does not certify any vendors, verifiers, or software. Any assurance, trust mark, or certification claiming ASVS compliance is not officially endorsed by OWASP"*. Por isso, aqui o ASVS nível 1 é **meta de verificação, não certificação**. O mesmo texto pede que requisitos não aplicáveis sejam registrados como tal (seção 4).
- **NIST SSDF** organiza práticas de desenvolvimento seguro. Não é requisito técnico da aplicação.
- **Cheat Sheet Series** dá orientação de implementação, não requisito.
- **CWE** classifica fraquezas (tipos de erro), não vulnerabilidades concretas.
- **CVE** é um identificador público atribuído a uma vulnerabilidade específica e catalogado pelo CVE Program. **Não é uma organização, um selo nem uma certificação.** **A ausência de CVE não prova segurança.** Muitas falhas nunca recebem CVE, e algumas têm só o ID do mantenedor. Exemplos reais deste projeto:
  - GHSA-2xp9-vwfh-vxw4, RCE crítico na Image Optimization do Next: a API de advisories do repositório do Next devolveu `cve_id: null` às 2026-10-02T02:36Z (versions.json também o lista sem CVE);
  - GHSA-67mh-4wv8-2f99, do esbuild, voltou da API do GitHub Advisory Database com `cve_id: null` (reconferido na revisão, entre 2026-10-02T02:30Z e 02:36Z; [findings.md](findings.md), PD-SEC-004).
- **NVD** acrescenta dados a um CVE já existente. Não é a fonte primária da correção.
- **CISA KEV** registra exploração conhecida. Estar fora do KEV **não** significa que uma falha não é explorada.
- **GitHub Advisory Database e advisories dos mantenedores** são a fonte para versões afetadas e corrigidas. Se o advisory e o post oficial divergirem, registrar os dois. Exemplo: nos advisories do Next de 2026-09-30, a API mostra `patched: 16.3.?`, e a versão exata 16.3.8 vem do post https://nextjs.org/blog/september-2026-security-release (versions.json).

## 2. Escopo de verificação ASVS 5.0.0

- **Texto usado:** arquivos `0x10-V1-...md` a `0x26-V17-...md` da tag `v5.0.0`. Contagem por expressão regular sobre as tabelas de requisitos: **345 requisitos**, dos quais **70 são de nível 1**.
- **Distribuição dos requisitos de nível 1:** V1 8 · V2 4 · V3 8 · V4 2 · V5 4 · V6 13 · V7 6 · V8 4 · V9 4 · V10 5 · V11 3 · V12 3 · V13 1 · V14 2 · V15 3 · V16 0 · V17 0.
- **Alvo:** todos os requisitos de nível 1 aplicáveis (seção 4), mais os de nível 2 escolhidos pelo modelo de ameaças (seção 5). Exemplos destes últimos: CSP, `nosniff`, `frame-ancestors`, menor privilégio no banco, allowlist de destinos externos e erros genéricos.
- **Por que o nível 1 sozinho não basta:** no ASVS 5.0.0, vários controles centrais para este portal são de nível 2: 3.4.3 (CSP), 3.4.4 (`nosniff`), 3.4.6 (`frame-ancestors`), 13.2.2 (menor privilégio entre componentes), 15.3.2 (não seguir redirects) e 16.5.1 (mensagem de erro genérica). Nenhum requisito do V16 (logs e erros) é de nível 1.
- **Como o status evolui:** "implementado" só quando houver código ou configuração no repositório **e** a verificação indicada passar. Até lá, "planejado". Um check sem achados não prova ausência de vulnerabilidade.

## 6. Regras de bloqueio de release (prompt mestre, seção 9)

Bloqueiam release:

- vulnerabilidade Crítica ou Alta, aplicável e não mitigada;
- exploração conhecida aplicável (por exemplo, presente no KEV);
- falha de integridade financeira (número errado, dupla contagem, mistura de recortes).
